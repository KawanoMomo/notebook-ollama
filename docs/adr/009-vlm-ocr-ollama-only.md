# ADR-009: VLM/OCRはOllama一本+エンジン抽象化とする

- **ステータス**: 承認
- **カテゴリ**: external-dep
- **日付**: 2026-07-20
- **出典**: VLM図説明・OCR設計 `docs/specs/2026-07-20-vlm-figure-ocr-design.md`

## コンテキスト

図の説明文生成とスキャンPDFのOCRをどの推論基盤で実行するか。開発機はRTX 2080 Ti(Turing, 11GB)で bf16/flash-attn 非対応という制約がある。

## 検討した選択肢

### A) Ollama一本(既存ゲートウェイにVLM呼び出しを追加)

- メリット: 追加依存ゼロ。モデル選択・切替UIの既存パターンをそのまま流用。アプリの「Ollama一本」アーキテクチャを維持
- デメリット: OCR専用モデル比で精度が劣る可能性(特に細かい日本語)

### B) OCR専用エンジン併用(PaddleOCR/RapidOCR等)

- メリット: スキャン文書の精度・CPU実行
- デメリット: Python依存の増加、二系統の運用

### C) Unlimited-OCR等の専用GPUスタック(vLLM/SGLang)

- メリット: 最高精度
- デメリット: Turing非対応の公算大(bf16/flash-attn前提)。検証コスト高

## 決定

A を採用する。呼び出しは `OcrEngine` / `FigureDescriber` インターフェースで抽象化し、B/C への将来差し替えに備える。C は半日タイムボックスの検証スパイクのみ実施し、結果を dev_logs に記録して本体には組み込まない。

## 結果

(2026-07-25 実装・マージ済み、PR #25 — 詳細は [[ECN-002_VLM図説明とスキャンPDF-OCR|ECN-002]])

- 決定どおり `OcrEngine` / `FigureDescriber` インターフェースで抽象化し、
  実装は Ollama 一本(`8f24bcd`、`05410ff`)
- **最大の想定漏れは「LLM の失敗は例外で返ってこない」こと**(`82a422a`)。
  VLM は読めない画像に対して「申し訳ありませんが、この画像からテキストを
  読み取ることはできません」という**もっともらしい日本語**を返す。これが本文として
  索引に載り、検索でヒットして回答の根拠になっていた。
  抽象化の設計時にエラー経路は考えたが、**「成功に見える失敗」**は想定していなかった
- `vision_model` の実行時変更に追従しない問題(`a0c8d70`)。エンジンが起動時の
  設定値を掴んでいた → Lazy 化で修正
- 抽象化そのものは Stage 3/4 でも差し替え不要で、**インターフェースの粒度は妥当**だった
- ADR で予定していた「案C の半日タイムボックス検証スパイク」は**実施していない**
  (Ollama 一本で要件を満たせたため不要と判断)


## 教訓

- **LLM を部品として使うとき、妥当性検査を保存直前に必ず置く。** try/except は
  通信・パースの失敗しか捕まえない。拒否応答・ハルシネーションは
  「正常な応答」として返るため、出力の内容そのものを検査する層が要る
- **設定値の解決は実行時に寄せる。** 起動時に解決すると、ユーザーからは
  「設定を変えても効かない」というバグに見える。モデル選択のように
  UI から変えられる値は特に
- 外部エンジンの抽象化は**インターフェースを細くする**ほど差し替え余地が残る。
  今回 `OcrEngine` / `FigureDescriber` を2つに分けたことで、
  OCR だけ別実装にする選択肢が残っている
