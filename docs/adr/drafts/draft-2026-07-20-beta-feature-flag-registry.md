# ADR-draft: 機能提供はコード内フラグレジストリ+設定オプトインのベータ機構とする

- **ステータス**: 提案(ドラフト・未採番)
- **カテゴリ**: アーキテクチャ/リリース管理
- **日付**: 2026-07-20
- **出典**: 汎用ベータ機能フレームワーク設計 `docs/specs/2026-07-20-beta-feature-flags-design.md`

## コンテキスト

影響範囲の大きい機能をオプトインのベータとして提供し、評価後に簡単にGA昇格したい。フラグ定義の置き場所と昇格動線の設計が必要。

## 検討した選択肢

### A) コード内レジストリ宣言 + settings_storeオプトイン

- メリット: フラグの追加・昇格・廃止がすべてgit履歴とコードレビューに乗る。GA昇格は `stage: 'beta'→'ga'` の1行変更で完了(ゲートは共通ヘルパ経由なので掃除不要)。定義と実装の乖離が起きない
- デメリット: 昇格にコード変更(コミット)が必要

### B) DB/設定ファイルにフラグ定義を持つ(ランタイム昇格)

- メリット: 再起動だけで昇格できる
- デメリット: 定義がコード外に漏れ、どの版でGAになったか追跡困難。ゲート撤去時に定義との整合が壊れやすい

### C) 環境変数ベース

- メリット: 実装最小
- デメリット: UIから操作できずオプトイン体験にならない。個人アプリの利用形態に不適

## 決定

A を採用する。ゲートは必ず `is_enabled`/`require_feature` を経由、ベータ期間のデータはベータ非依存スキーマで作成(昇格時マイグレーション不要)、OFF時もデータは保持し露出のみ消す、を規約とする。第1号は表・図シリーズ共通フラグ `table-figure-rag`。
