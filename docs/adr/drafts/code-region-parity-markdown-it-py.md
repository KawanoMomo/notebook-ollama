# ADRドラフト: BE/FE のコード領域判定を markdown-it-py で同一アルゴリズムに揃える

- **ステータス**: 提案(未採番)
- **カテゴリ**: dependency
- **日付**: 2026-08-07
- **出典**: 出典表示の刷新 `docs/specs/2026-08-07-citation-evidence-ui-design.md` §3.1.1 / §3.2

## コンテキスト

根拠スパン解決は、回答本文中の `[^n]` の**出現順序**(`answer_occurrence`)で BE のスパンと FE のバッジを対応付ける。したがって **BE と FE が「どのマーカーを数えるか」で完全に一致していなければならない**。マーカーはコードブロック・インラインコードの中にも現れるため、両者は「コード領域の除外規則」を共有する必要がある。

- **FE** は `markdown-it`(`html: false`)でレンダリングした HTML に対し、`<code>` / `<pre>` の外側だけを置換する。つまり **markdown-it 本体が判定のオラクル**である。
- **BE** は `core/generation/evidence_spans.py` の `mask_code_regions` が、CommonMark のブロック構造を**手書きで走査**して同じ判定を再現しようとしている。

この二重実装がズレると、ズレ地点以降のすべての `answer_occurrence` が1つずつずれ、**別の主張の根拠を枝番付きで表示する**(ハイライト機能の信頼性を根本から損なう)。

### 実測された事実

共有フィクスチャ 43 形状では BE/FE が一致していたが、範囲外の 29 形状を追加検証したところ **9 件の不一致**が実証された。

| 形状 | 頻度 |
|---|---|
| 番号付きリスト配下の4スペースフェンス(内部に空行) | 高 |
| 同上・`~~~` フェンス | 高 |
| 段落を中断する順序リスト風の行 | 中 |
| リンク参照定義として消える `[^2]: http://...` | 中 |
| リスト項目/見出しをまたぐインラインコード対 | 中 |
| setext 見出し直後のインデントコード | 低 |
| 引用ブロック内フェンスの lazy 継続 | 低 |
| CRLF の空行を段落境界と認識しない | 低 |

さらに重要な観察として、**従来「通っていた」同型ケースの一部は偶然だった**。ブロック走査が取りこぼしたフェンス対を、インラインコードのマスクがたまたま拾って辻褄が合っていただけで、チルダや空行入りでは崩れていた。つまりフィクスチャの緑は、判定規則の正しさを保証していなかった。

### 修正を3回試みて、3回とも「偶然の一致」に助けられていた

この論点の核心は反例の件数ではなく、**修正のたびに別の形状が壊れ、しかもテストが緑だった理由が毎回「別の判定が偶然拾っていたこと」だった**点にある。実際の経緯:

| 版 | 直したこと | 壊れたこと / 緑だった本当の理由 |
|---|---|---|
| `adbbd6c` | 行走査ベースへ全面書き換え、43形状のフィクスチャを整備 | 番号付きリスト配下の4スペースフェンスは、ブロック走査が取りこぼした ``` の対を**インラインコードのマスクが偶然拾って**一致していた。チルダや内部空行では崩れる |
| `cdb0c8f` | フェンス判定をコンテナ相対化(上記の高頻度2件を修正) | 「箇条書き → 空行 → 列0のコードブロック」という**最頻出級の形状**を破壊。リストを抜けた行にネストのインデントが適用され、コードが本文として数えられ、後続の本文がコード扱いになる両方向のズレ |
| 作業中の下書き | 有効コンテナの導入、桁数比較、close→reopen | フェンス**内の空行**が「コンテナより浅い行」と判定されフェンスを閉じていた。それでも手元のテストが通ったのは、閉じた後の内容を**インデントコード判定が偶然拾い直していた**ため。2スペースの箇条書きでは救済が効かず露呈 |
| `9c2d968` | 上記2件(空行・閉じフェンスの相対上限)を修正。フィクスチャを55形状に拡張 | 現時点で既知の不一致はスコープ外7件のみ |

つまり **3回連続で、テストの緑は判定規則の正しさを保証していなかった**。フィクスチャを増やすことでしか安全性を担保できず、そのフィクスチャは「思いついた形状」の集合でしかない。CommonMark のブロック構造は規則が相互作用するため、この方式では「次の反例」が出続ける。

高頻度の2件は `cdb0c8f`、その修正が生んだリグレッションと派生2件は `9c2d968` で修正済み。**残り7件(setext / 引用内 lazy 継続 / リスト割込 / インライン跨ぎ / リンク参照定義 / CRLF)は未修正**。

## 検討した選択肢

### 選択肢A: 手書きスキャナを維持し、反例が出るたびに直す(現状)

- 追加依存ゼロ。実行コストも最小(生成完了後の後処理で数ms)。
- 一方で CommonMark のブロック構造は、リストのコンテナ相対インデント、lazy continuation、setext 見出し、リンク参照定義、HTMLブロック、フェンスの info string など**規則が多く相互作用する**。今回9件出たことは、今後も出続けることを意味する。
- 漏れは静かに起きる。テストが緑でも、フィクスチャに無い形状で誤帰属する。

### 選択肢B: markdown-it-py を導入し、トークン列からコード領域を求める

- `markdown-it-py` は markdown-it の**公式 Python ポート**で、同一アルゴリズム・同一の CommonMark 準拠を謳う。block トークンの `map`(行範囲)と inline の `code_inline` トークンからコード領域を求めれば、FE と**構造的に**一致する。
- 依存が1つ増える(純Python、ネイティブ拡張なし)。パース時間は回答テキスト1本ぶんで、後処理の予算に収まる見込み(要実測)。
- 完全な同一性は保証されない(ポート間のバージョン差)。FE の `markdown-it` とメジャーバージョンを揃える運用が要る。

### 選択肢C: 判定を FE に一本化し、BE は出現位置を持たない

- BE は `[^n]` の出現順序を数えず、FE がレンダリング結果から出現位置を確定してサーバへ問い合わせる。二重実装そのものを消せる。
- ただし第1段(字句照合)は**生成直後にサーバ側で完結する**設計(spec §3.1.1)であり、これを崩すと spans の永続化・MCP 経由の応答(`core/mcp/tools/ask.py`)が成立しない。MCP クライアントは markdown-it を持たない。

## 決定(案)

**選択肢B** を推す。ただし Phase 1 ゲート(第1段の解決率実測)を通過してから着手する。

理由:
- ズレの影響が「静かな誤帰属」であり、[[016-pixel-native-explicit-failure]] で確立した「黙って劣化させない」方針と正面から衝突する。テストで守り切れない類の欠陥は、構造で消すべき。
- 選択肢C は spec の中核設計(サーバ側で完結する後処理)を崩すため採らない。
- 選択肢A を続ける場合でも、残り7件の反例は塞ぐ必要がある。その作業量は B の導入と大差ない見込みで、かつ将来の漏れが残る。
- 3回の修正で毎回「偶然の一致」に助けられていた事実が、**この方式ではテストが安全性の根拠にならない**ことを示している。判定のオラクルを1つ(markdown-it)に統一すれば、この問題は構造的に消える。

## 影響

- `core/generation/evidence_spans.py` の `mask_code_regions` を markdown-it-py ベースに置換。公開API(`iter_claim_occurrences` / `attach_evidence_spans`)は不変。
- `pyproject.toml` に依存追加。オフライン配布(PyInstaller)への影響を確認すること。
- 共有フィクスチャ `tests/fixtures/code_region_cases.json` はそのまま回帰テストとして機能する。BE/FE のバージョン整合を検査するテストを1本足す。
- FE 側の `markdown-it` を更新する際は、BE の `markdown-it-py` も追随させる運用ルールが必要。

## 未解決

- `markdown-it-py` と `markdown-it`(JS)のバージョン対応表をどう維持するか。
- パース時間の実測(長い回答＋多数のチャンクでの後処理予算)。
- 選択肢A を続ける判断をした場合の、残り7反例の修正見積り。
