# ADR-draft: 視覚索引構築の部分成功は単位ごとの独立性を意味する

- **ステータス**: 提案(ドラフト・未採番)
- **カテゴリ**: アーキテクチャ/エラー処理
- **日付**: 2026-07-30
- **出典**: PixelRAG式タイル索引と検索戦略の選択 `docs/specs/2026-07-29-pixelrag-tile-index-design.md` §9(部分成功はログ+スキップで構築継続)

## コンテキスト

視覚索引構築(`VisualIndexBuilder.build()`)は、ページ単位の埋め込み失敗をログ+スキップして構築を継続する「部分成功」を既定挙動とする(Stage 3から継続)。Stage 4 でタイル分割が加わり、1ページが複数タイルに分かれるようになったとき、「部分成功」の単位をページ単位のままにするか、タイル単位まで下げるかの選定が必要になった。

## 経緯: 計画の内部矛盾の発見とコントローラ裁定

実装中、実装者が正当に BLOCKED で停止した。

- `test_tile_embed_failure_skips_page_and_continues` は「1タイル失敗でも同ページの残タイルは処理される」(`skipped_pages=0, indexed_tiles=5`)を期待するテストだった
- しかし計画brief Step 3 の実装コードは、ページ内タイルループ全体を1つの `try/except` で囲んでおり、先頭タイルの失敗でページごと処理を中断する実装になっていた
- 実測: `BuildResult(indexed_pages=1, skipped_pages=1, indexed_tiles=3)` でテストFAIL(10 passed / 1 failed)

計画本文のテストと実装コードが相互に矛盾しており、実装者の裁量では解決できない状態だった。

## 検討した選択肢

### A) テストが正しい: try を2段に分割(分割失敗→ページ全体の失敗 / 埋め込み等の失敗→単位ごと)

- メリット: 3分割したページで先頭タイルの埋め込みが失敗しても、良好な残り2タイルは索引に反映される。「部分成功」という設計意図(spec §9)がタイル単位まで貫徹する
- デメリット: try/exceptの構造が1段から2段に増え、実装がやや複雑になる

### B) 実装コードが正しい: 1タイルでも失敗したらページ全体を失敗扱いにする

- メリット: 実装がシンプル
- デメリット: 3分割のページで先頭タイルの埋め込みが失敗しただけで、良好な残り2タイルまで丸ごと捨てることになる。spec §9 が意図する「部分成功で構築継続」という設計方針に反する

## 決定

A を採用する。**裁定: テストが正しく、実装コードが誤り。** spec §9 の部分成功は単位ごとの独立性を意図しており、3分割で先頭タイルの失敗により良好な2タイルを捨てるのは設計意図に反する。分割自体の失敗(タイル分割関数が例外を投げる場合)はページ全体の失敗として別段のtryで扱い、埋め込み等の失敗は単位(タイル)ごとに捕捉する。

計画ファイル本体(`docs/superpowers/plans/2026-07-29-pixelrag-tile-index.md` Task 6 Step 3)も、この裁定に合わせて修正した。人間への確認は不要と判断した: 両側とも計画本文由来の記述であり、どちらが正しいかはspec §9の明文から一意に決まる技術的な誤記訂正だった。

## 結果

(2026-07-30 実装・実機検証済み)

- 決定どおり実装。コントローラ機能スモーク(実PDF・実Qdrant)で `BuildResult(indexed_pages=2, skipped_pages=0, indexed_sources=1, indexed_tiles=6)` を確認。進捗はページ基準 `[(1,2),(2,2)]`。`tiles/{1,2}-{0,1,2}.png` の6件生成、**tile構築で `pages/` は作られない**(単位間の相互不上書きを確認)
- ベクトル6件、`tile_index` は全件 `{0,1,2}` のいずれかで `None` 混入なし

### 併せて記録すべき教訓: 「部分成功」は「全滅を成功として通知してよい」ではない

実機検証(Task 15b)で、この判断とは別の角度から関連する不具合が見つかった。**視覚索引構築が全ページ失敗しても、フロントに「構築が完了しました」という成功トーストが表示される**という不具合(不具合A)である。

- 当初コントローラが指示した判定式 `indexed_pages==0 and skipped_pages>0` は、**レンダリング全滅を取りこぼす**。ビルダはファイル欠落・破損PDFのソースを `pages_by_source` に登録せず丸ごと `continue` するため、両カウンタ(`indexed_pages` / `skipped_pages`)とも一切増えず `0/0` になり「対象なし」と誤判定されてしまう
- **レンダリング自体が失敗したソースはページカウンタが一切増えない**ため、`skipped_pages` を代理指標にすると取りこぼす
- 裁定: `BuildResult.target_sources`(対象ソース数)を追加し、`target_sources > 0 and indexed_pages == 0` を失敗と判定するよう修正した。4境界(render全滅→True / embed全滅→True / 対象0件→False / 部分成功→False)すべて期待どおりであることをコントローラが検証した

## 教訓

- 「単位ごとの部分成功」を設計するときは、失敗の粒度を「その単位の処理が試みられたか」まで含めて定義しないと、カウンタの意味論に穴ができる。「試みてスキップ」と「試みられずカウントに現れない」は別の状態であり、後者を代理指標で判定すると全滅ケースを取りこぼす
- 計画(plan)のテストコードと実装擬似コードが矛盾したまま実装フェーズに進んでしまう場合がある。実装者が「計画が指示するテストを通すために計画が指示する実装を書くと矛盾する」ことに気づいてBLOCKEDで止まる規律は機能した。裁定の可否は「spec本文から一意に決まるか」を基準にし、一意に決まらない場合のみ人間に確認する
