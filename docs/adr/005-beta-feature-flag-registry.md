# ADR-005: 機能提供はコード内フラグレジストリ+設定オプトインのベータ機構とする

- **ステータス**: 承認
- **カテゴリ**: release
- **日付**: 2026-07-20
- **出典**: 汎用ベータ機能フレームワーク設計 `docs/specs/2026-07-20-beta-feature-flags-design.md`

## コンテキスト

影響範囲の大きい機能をオプトインのベータとして提供し、評価後に簡単にGA昇格したい。フラグ定義の置き場所と昇格動線の設計が必要。

## 検討した選択肢

### A) コード内レジストリ宣言 + settings_storeオプトイン

- メリット: フラグの追加・昇格・廃止がすべてgit履歴とコードレビューに乗る。GA昇格は `stage: 'beta'→'ga'` の1行変更で完了(ゲートは共通ヘルパ経由なので掃除不要)。定義と実装の乖離が起きない
- デメリット: 昇格にコード変更(コミット)が必要

### B) DB/設定ファイルにフラグ定義を持つ(ランタイム昇格)

- メリット: 再起動だけで昇格できる
- デメリット: 定義がコード外に漏れ、どの版でGAになったか追跡困難。ゲート撤去時に定義との整合が壊れやすい

### C) 環境変数ベース

- メリット: 実装最小
- デメリット: UIから操作できずオプトイン体験にならない。個人アプリの利用形態に不適

## 決定

A を採用する。ゲートは必ず `is_enabled`/`require_feature` を経由、ベータ期間のデータはベータ非依存スキーマで作成(昇格時マイグレーション不要)、OFF時もデータは保持し露出のみ消す、を規約とする。第1号は表・図シリーズ共通フラグ `table-figure-rag`。

## 結果

(2026-07-23 実装・マージ済み、PR #24 — 詳細は [[ECN-001_表・図サイドカー抽出とベータ機能フラグ基盤|ECN-001]])

- 決定どおり `core/features.py` のレジストリ + `settings.json` オプトインで実装。
  第1号フラグ `table-figure-rag` を表・図シリーズ Stage 1〜4 の全体で共有し、
  4段階の開発中ずっと未完成状態を隠せた。**枠組みとしては意図どおり機能した**
- 規約の3点(ベータ非依存スキーマ / OFF時もデータ保持 / ゲートは必ず
  `is_enabled`・`require_feature` 経由)はいずれも守られ、Stage 4 まで
  スキーママイグレーションは発生しなかった
- **ゲートの掛け漏れが繰り返し発生した**。PR #24 の後半5コミット中3件、
  PR #25 でも1件(`a7cf317` ベータOFFでも `PUT /settings/vision-model` が200)が
  同じ種類の指摘だった。レジストリがあること自体は掛け漏れを防がない
- GA昇格済みフラグへのオプトイン変更が 500 を返す不具合を修正(`04c6f8c`、400 が正)


## 教訓

- **フラグ基盤を作っても「どこに掛けるか」は自動化されない。** 機能追加時に
  「その機能に到達する経路をすべて数え上げる」作業が別途要る。表示経路が
  2つ(カード表示/全文表示)あることを見落として同種の指摘を2回受けた
- ベータ基盤を**第1号の適用先と同じPRで入れた**のは正解だった。適用先が同時に
  あることで「ゲートを通す」規約が具体的な形で確定した
- 昇格後(GA化)の挙動まで含めて設計しておくこと。`04c6f8c` は
  「フラグが消えた後にオプトインAPIを叩かれる」ケースの考慮漏れだった
