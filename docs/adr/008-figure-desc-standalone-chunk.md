# ADR-008: VLM図説明は独立チャンク方式で検索に乗せる

- **ステータス**: 承認
- **カテゴリ**: data-model
- **日付**: 2026-07-20
- **出典**: VLM図説明・OCR設計 `docs/specs/2026-07-20-vlm-figure-ocr-design.md`

## コンテキスト

VLMが生成した図の説明文を検索に乗せる格納方法の選定。取込後(describe段・手動「図を解析」)に説明文が生まれるため、既存チャンクへの影響が論点。

## 検討した選択肢

### A) 独立チャンク化(図1つ=1チャンク)

- メリット: 既存チャンク不変で再埋め込み不要。埋め込みは新規分のみ。図単位の引用が可能。Stage 1保存済みクロップへの後追い処理だけで成立(再取込不要)
- デメリット: チャンク種別(kind)の区別が必要

### B) 同ページ既存チャンクの本文に追記

- メリット: 文脈と一体化
- デメリット: チャンク本文が変わり再埋め込みが必要。チャンクID・引用の安定性が下がる

### C) 両方(独立チャンク+本文参照マーカー)

- メリット: 検索の当たりが広い
- デメリット: 再埋め込みが結局発生し、複雑度に見合わない

## 決定

A を採用する。`chunks.kind='figure_desc'` で区別し、`chunk_assets.desc_chunk_id` で図アセットと相互リンクする。ベータフラグOFF時は kind でフィルタして検索から除外する。

## 結果

(2026-07-25 実装・マージ済み、PR #25 — 詳細は [[ECN-002_VLM図説明とスキャンPDF-OCR|ECN-002]])

- 決定どおり `chunks.kind='figure_desc'` + `chunk_assets.desc_chunk_id` の
  相互リンクで実装(`5af555e` マイグレーション、`67ad85e` パイプライン統合)
- 独立チャンクにしたことで、**ベータOFF時に kind で切り離せる**という設計意図は
  実装できた。ただし**その除外処理自体が最初は漏れていた**(`9c62a96` で修正)。
  「切り離せる構造にした」ことと「実際に切り離している」ことは別だった
- 同コミットで「閲覧のたびに再OCRが走る」問題も修正。生成結果を保存せず
  毎回作り直していた
- 元チャンク本文への追記案を採らなかったのは正解だった。追記していたら
  上記の切り離しは不可能で、フラグOFFがデータ破壊を意味することになっていた


## 教訓

- **「あとで切り離せる構造」は、切り離す処理を同時に書いて初めて成立する。**
  構造だけ用意して分岐を書き忘れると、設計上の利点が実現しない
- 生成コストのかかる派生データ(VLM出力)は、**保存の有無を明示的に設計する**。
  「必要なときに作る」と書くと、閲覧のたびに作る実装になりうる
- `kind` による種別分けは、検索除外・表示制御・再生成判定の3つで使い回せた。
  データモデルに1列足す判断としては効率が良かった
