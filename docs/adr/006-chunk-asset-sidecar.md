# ADR-006: 表・図はチャンク紐付きサイドカーアセット方式で保存する

- **ステータス**: 承認
- **カテゴリ**: data-model
- **日付**: 2026-07-20
- **出典**: 表・図サイドカー設計 `docs/specs/2026-07-20-pdf-table-figure-sidecar-design.md`

## コンテキスト

PDFの表・図はプレーンテキスト抽出で欠損する。表・図の実体(HTML/画像)をどこに保存し、検索・生成とどう結び付けるかの選定が必要。

## 検討した選択肢

### A) chunk_assets テーブル + ファイル保存(サイドカー)

- メリット: チャンク構造・ベクトルストアを変えずに追加できる。ソース単位の一括削除が容易。スライドPDF併産(`<id>.slides.pdf`)と同型で運用が揃う
- デメリット: チャンクとの紐付け整合を自前管理する必要がある

### B) チャンク本文にすべて埋め込む(HTML直挿入)

- メリット: 紐付け管理不要
- デメリット: 埋め込みトークンを浪費し検索品質が下がる。画像は表現不可

### C) ベクトルストア(Qdrant)のpayloadに保存

- メリット: 検索ヒットと同時に取得できる
- デメリット: Qdrantが実体ストアになり肥大化。SQLite側とのJOIN運用(引用・プレビュー)と乖離

## 決定

A を採用する。`chunk_assets`(id/source_id/chunk_id/kind/page/bbox/html/md_snippet/image_path)+`data/assets/<source_id>/` にファイル保存。ベクトルには乗せない。再取込・ソース削除時は行とディレクトリを一括削除して再構築する(冪等)。

## 結果

(2026-07-23 実装・マージ済み、PR #24 — 詳細は [[ECN-001_表・図サイドカー抽出とベータ機能フラグ基盤|ECN-001]])

- 決定どおり `chunk_assets` テーブル + `data/assets/<source_id>/` のファイル保存で実装
  (`2456fd4` storage、`8f1ce8a` 取込配線)。**ベクトルには乗せない**方針も維持
- **再取込の冪等性が狙いどおり単純になった**。「行とディレクトリの一括削除 →
  再構築」だけで済み、部分更新のための差分計算が不要だった
- ただし**ソース削除時のアセット掃除が漏れていた**。Stage 3 のレビューで発覚し
  `97ab961` で修正(Stage 1 由来の不具合)。取込側の冪等性は考えたが、
  **ライフサイクルのもう一方の端(削除)を見落とした**
- Stage 2 で `desc_chunk_id` 列を足して図説明チャンクと相互リンクする拡張が
  入ったが(`5af555e`)、サイドカー方式そのものは変えずに済んだ


## 教訓

- **サイドカー方式は「再構築の単位」を粗くできるのが本質的な利点。** 行と
  ディレクトリを丸ごと捨てて作り直せるので、差分同期のバグが入る余地が無い
- **冪等性は取込側だけでなく削除側も設計する。** 「作り直せる」ことに気を取られ、
  「消したときに残らない」ことの確認が抜けた。ライフサイクルは両端で閉じること
- 後続ステージでの列追加(`desc_chunk_id`)を吸収できたのは、アセットを
  独立テーブルに置いたおかげ。本文チャンクに埋めていたら再取込が必要だった
