# ADR-002: ページ遷移の記録は録音セッションの汎用タイムラインマーカー機構で行う

- **ステータス**: 承認
- **カテゴリ**: architecture
- **日付**: 2026-07-06
- **対象プロジェクト**: NotebookOllama
- **関連ADR**: draft-2026-07-06-source-links-generic-parent-child
- **出典**: 発表モード設計 `docs/specs/2026-07-06-presentation-mode-design.md`(案A/B/C比較)

## コンテキスト

発表モードでは「何ページ目を表示中に何を話したか」を記録するため、録音タイムライン上の
ページ遷移時刻が必要。既存の録音セッション(recorder/LiveCaption/ソース化パイプライン)に
どう組み込むかが論点。

## 検討した選択肢

### A) 録音セッションを発表専用に拡張

- 概要: 録音セッションが deck_source_id とページ遷移履歴を直接保持
- メリット: 実装最短
- デメリット: 汎用機能(録音)が特定用途(発表)の知識を持ち、結合が増える

### B) 発表専用セッションの新設

- 概要: PresentationSession を新設し録音を内部利用
- メリット: 関心分離が最も綺麗
- デメリット: セッション管理・WS・ソース化の重複実装。v1コストとリグレッションリスク最大

### C) 汎用タイムラインマーカー機構(採用)

- 概要: 録音セッションに `{kind, value, at_ms}` を記録する汎用APIのみ追加。
  「kind=page がページ遷移」という意味づけは発表モード側だけが知る
- メリット: 録音側は発表を知らない(結合最小)。実装規模はAと同等。将来の別種マーカー
  (「ここ重要」、章区切り等)にそのまま使える
- デメリット: 抽象が1枚増える

## 決定

C を採用。`at_ms` はサーバー側で録音タイムライン(既存のmic/system共有epoch)から算出し、
クライアント時計に依存しない。マーカーは録音確定時に `source_markers` テーブルへ永続化し、
チャンク化時に `chunks.page` へページ番号を割り当てる(録音ソースにおける page の意味=
「親発表資料の何ページ目で話したか」)。

## 結果

(2026-07-20 実装・マージ済み、PR #19 — 詳細は [[ECN-008_発表モード|ECN-008]])

- 決定どおり、`at_ms` はサーバー側で既存の mic/system 共有 epoch から算出し、
  クライアント時計に依存しない実装にした。マーカーは `source_markers` に永続化し、
  チャンク化で `chunks.page` に割り当てる
- **ページ値の検証が甘く、不正値で変換が恒久 ERROR に落ちる不具合が出た**
  (`fix(recording)`)。int-parse 基準に統一して修正。マーカーは外部入力
  (FE から送られる) なので、境界の検証は録音本体の成否に直結する
- 発表確定に失敗しても録音停止を完走させる設計に途中で変更した
  (`fix(recording)`)。当初は確定失敗が stop を巻き添えにしていた
- 引用からページ別発言の逆引きが機能している(実機検証 AC7)


## 教訓

- **時刻はサーバー側の既存タイムラインから算出する。** クライアント時計を
  信じると、時刻ずれ・一時停止・タブ非アクティブで紐付けが静かにずれる。
  「ずれても気づけない」種類の不具合になる
- **付随データ(マーカー)の検証失敗で本体(録音)を落としてはいけない。**
  ユーザーが失って痛いのは録音であり、紐付けは後から直せる。処理の順序と
  失敗時の巻き戻し範囲は、データの価値で決める
- 外部入力を受けるカラムは、パース基準を1箇所に統一する。検証の書き方が
  経路ごとに違うと、片方だけ通り抜ける
