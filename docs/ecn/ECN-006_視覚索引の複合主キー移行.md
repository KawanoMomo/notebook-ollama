# ECN-006: SQLite テーブル再作成によるスキーマ移行 (複合主キー化)

- **ステータス**: 適用済 (PR #27 内、2026-08-02 マージ)
- **種別**: 改善
- **対象コミット**: `28cb351`
- **影響ファイル**: `core/storage/migrations.py`
- **横断価値**: **MEDIUM** — SQLite を使う全プロジェクトに当てはまる型

## コンテキスト

視覚索引を単位 (page / tile) ごとに持つため、以下の主キー変更が必要になった。

| テーブル | 変更前 | 変更後 |
|---|---|---|
| `visual_index_meta` | `PRIMARY KEY(notebook_id)` | `PRIMARY KEY(notebook_id, unit)` |
| `visual_index_sources` | `PRIMARY KEY(source_id)` | `PRIMARY KEY(source_id, unit)` |

**SQLite には主キーを変更する `ALTER TABLE` が無い。** 列の追加はできても、
制約の変更はテーブルを作り直すしかない。本リポジトリでは初のケースだった。

## 対策

公式が推奨する4段階 (CREATE new → INSERT SELECT → DROP → RENAME):

```python
conn.execute("DROP TABLE IF EXISTS visual_index_meta_new")
conn.execute(_VISUAL_INDEX_META_NEW_DDL)
conn.execute(
    "INSERT INTO visual_index_meta_new(notebook_id, unit, embedding_model, built_at) "
    "SELECT notebook_id, 'page', embedding_model, built_at FROM visual_index_meta"
)
conn.execute("DROP TABLE visual_index_meta")
conn.execute("ALTER TABLE visual_index_meta_new RENAME TO visual_index_meta")
```

既存行はすべて `unit='page'` として移行する (Stage 3 の索引 = ページ単位のため)。

### 要点1: autocommit 接続下での原子性

本リポジトリの `connect()` は `isolation_level=None` (**autocommit**) で、
既存のマイグレーションは `commit` を呼ばない設計になっている。

しかしテーブル再作成は**複数文にまたがる**。途中で落ちると
**テーブルが消えた状態で残る** (DROP は済んだが RENAME 前)。
この関数だけは明示的にトランザクションを張る:

```python
owns_tx = not conn.in_transaction
if owns_tx:
    conn.execute("BEGIN IMMEDIATE")
try:
    ...
    if owns_tx:
        conn.execute("COMMIT")
except Exception:
    if owns_tx:
        conn.execute("ROLLBACK")
    raise
```

`conn.in_transaction` を見ることで、**呼び出し側が既にトランザクション中なら
その外側に委ねる** (二重 BEGIN を避ける)。

### 要点2: 冪等性の判定材料

`unit` 列の**存在**を見て判定する。マイグレーションのバージョン番号ではなく
スキーマの実体を見るため、途中適用や手動操作の後でも正しく動く。

```python
meta_needs = not _has_column(conn, "visual_index_meta", "unit")
sources_needs = not _has_column(conn, "visual_index_sources", "unit")
if not meta_needs and not sources_needs:
    _ensure_visual_index_indexes(conn)   # インデックスの補完のみ
    return
```

### 要点3: 外部キーの確認を省略しない

`PRAGMA foreign_keys` が ON の状態でテーブルを DROP すると、参照している側が
壊れる。**`schema.sql` と `migrations.py` の全文を確認**し、`visual_index_*` が
FK を持たず他テーブルからも参照されていないことを確かめた上で、
`foreign_keys` の OFF/ON を**あえて省略**した (その旨を docstring に明記)。

## 結果

- 既存の Stage 3 索引 (`unit='page'`) を保持したまま移行完了
- 移行前後で `pages_visual` の point ID は不変 → **Qdrant 側の再構築も不要**
- 冪等性・原子性・途中適用のテストを `tests/unit/` に追加

## 教訓

- **SQLite で制約を変えるときはテーブル再作成しかない。** 「あとで直せる」と
  思って緩い主キーで作ると、後から必ずこの手順が必要になる
- **autocommit 接続でのマルチステートメント移行は、明示トランザクションが必須。**
  「既存のマイグレーションが commit を呼んでいないから」という一貫性より、
  **落ちたときにテーブルが消える**方が重大
- **`conn.in_transaction` を見て所有権を判定する型**は再利用価値が高い。
  呼び出し側がトランザクションを張っているかどうかに関わらず正しく動く
- **冪等判定はバージョン番号よりスキーマの実体を見る方が壊れにくい。**
  バージョン管理テーブルは手動操作で簡単にずれる
