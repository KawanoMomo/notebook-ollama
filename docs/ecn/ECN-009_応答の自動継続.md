# ECN-009: 応答の自動継続 (assistant prefill)

- **ステータス**: 適用済 (PR #23、2026-07-23 マージ、issue #22)
- **種別**: 機能追加
- **対象コミット**: 20コミット (先頭 `b6fbef7c` / 末尾 `af461d7b`)
- **規模**: 49ファイル (core/apps 24 / tests 8 / docs 3)
- **影響ファイル**: `core/generation/stream.py`, `core/storage/messages_repo.py`,
  `core/storage/migrations.py`, `apps/api/routers/conversations.py`,
  `core/mcp/tools/ask.py`, `apps/web/src/lib/stores/chat.svelte.ts`

## コンテキスト

`num_predict` (応答トークン上限) に達すると、回答が文の途中で切れる。
利用者から見ると「モデルが答えきれなかった」のか「上限で切れた」のかが
分からず、続きを得る手段もなかった。

## 対策

### 1. 継続は assistant prefill (ADR-012)

Ollama は**末尾の assistant メッセージの続きから**生成する。
`done_reason == "length"` を検出したら、それまでの本文を末尾 assistant
メッセージとして積んで再送する。

```python
req_messages = list(messages)
if answer_parts:
    req_messages.append({"role": "assistant", "content": "".join(answer_parts)})
```

**採用しなかった案**: 「続きを書いて」と user メッセージで頼む方式
(モデルが前置きを繰り返す・文体が変わる)。

自動継続の回数は設定 `auto_continue_max` (既定2、0-5)。

### 2. truncated は messages カラムで永続化 + 追記更新 (ADR-013)

打ち切り状態を `messages.truncated` に持ち、手動継続は**最終 assistant
メッセージを追記更新**する (新しいメッセージを足さない)。
会話の見た目が「1つの回答」のまま伸びる。

### 3. MCP にも同じ継続を適用

`ask` ツールにも同じループを入れた。ただし**継続ラウンドの失敗は
graceful degradation** —— 途中までの本文を捨てず、注記を付けて返す。

```python
except AppError:
    if round_idx == 0:
        raise          # 1回目の失敗は本物のエラー
    answer_parts.extend(round_parts)   # 継続の失敗は途中本文を守る
    truncated = True
    continuation_failed = True
```

## 問題の詳細

| コミット | 症状 |
|---|---|
| `fix(generation)` 注記文言 | 継続エラー時の注記が実態と違う (「上限に達した」と書くが実際は継続失敗) |
| `fix(storage)` not-found | `update_message_content` が存在しない ID で黙って成功していた + `updated_at` 未更新 |
| `fix(api)` 履歴 dedup | 手動継続で**履歴の重複除去が正しいメッセージを消していた** |
| `fix(web/store)` 旧注記 | 手動継続のシード本文に前回の打ち切り注記が混入 → prefill が注記の続きを書く |

**`fix(web/store)` が最も厄介**: 打ち切り注記 (「上限に達したため打ち切られ
ました」) を本文に含めたまま prefill すると、モデルが**注記の続き**を書き始める。
継続前に注記を除去する必要があった。

## 教訓

- **prefill 方式では「モデルに見せる本文」と「利用者に見せる本文」を分ける。**
  UI 都合で足した注記をそのまま prefill すると、モデルはその続きを書く。
  表示用の装飾は生成入力から必ず外す
- **リトライ/継続の失敗は、初回の失敗と区別する。** 初回は本物のエラーとして
  投げてよいが、継続の失敗で**すでに得た本文を捨てるのは損失**。
  「途中まで + 事情を説明する注記」が正しい落とし所
- **状態を1カラム足すだけの機能でも、更新系の穴は出る。** `update_message_content`
  の not-found を黙って通す実装は、呼び出し側のバグを隠す
- **「1つの回答が伸びる」という見た目を選ぶと、追記更新が必要になる。**
  メッセージを増やす方が実装は簡単だが、会話ログが継続回数だけ分割される
