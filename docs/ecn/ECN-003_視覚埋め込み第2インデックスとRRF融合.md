# ECN-003: 視覚埋め込み第2インデックスとRRF融合 (Stage 3)

- **ステータス**: 適用済 (PR #26、2026-07-29 マージ)
- **種別**: 機能追加 + 不具合修正
- **対象コミット**: `40ab89e5..0b4e3258` (29コミット)
- **規模**: 86ファイル、+5,001 / -216
- **影響ファイル**: `core/visual/` (新設), `core/storage/visual_store.py`,
  `core/retrieval/search.py`, `core/accel/`, `apps/web/` (視覚インデックスModal)

## コンテキスト

ECN-002 で図は言語化できたが、**言語化を経由する時点で情報が落ちる**。
レイアウト・図中の位置関係・表の視覚的構造は、テキスト化した瞬間に失われる。
ページ画像そのものをベクトル化して検索できるようにするのがこの変更の狙い。

Ollama は画像埋め込みモデルに対応していないため、**「Ollama 一本」原則の初めての
例外**を作る判断を伴った (ADR-011)。

## 対策

### 1. Qdrant 別コレクション + RRF 融合 (ADR-010)

`pages_visual` コレクションを新設。テキスト検索結果と **RRF (Reciprocal Rank
Fusion, k=60)** で融合し、`(source_id, page)` をキーに吸収する。

- `c3f4d98` `VisualPageStore` (**既存 `VectorStore.client` を共有**)
- `4d6ed1d` RRF融合の純関数 (重複排除つき)
- `80b7cbe` 視覚ページ検索のRRF統合とページ→チャンク展開

> [!important] Qdrant ローカルモードの制約
> **1パス = 1クライアント** (ファイルロック)。2つ目のコレクションを足すときは
> 新しいクライアントを作らず、既存の `VectorStore.client` を渡す必要がある。

### 2. transformers でオンデマンド実行 (ADR-011)

`--extra visual` の別依存として `sentence-transformers` を導入。
オンデマンドロード + アイドルアンロード (watchdog 60秒間隔) で 11GB VRAM を
チャットLLMと共有する。

## 問題の詳細 — 計算負荷が実機を壊した

この PR の後半コミットの大半は**機能ではなく負荷制御**に費やされた。

| コミット | 症状 | 対策 |
|---|---|---|
| `65a949a` | fp32 ロードでサーバープロセスが OOM 即死 (実機2回) | チェックポイントのネイティブ dtype である **bfloat16** に変更 |
| `4dc2a3b` | エンコーダが常駐したまま解放されない | アイドルアンロードの定期発火を追加 |
| `93dbca5` | **ロード/アンロードのスラッシング** (20分でロード8回) | 埋め込み実行中の watchdog アンロードを禁止 (**in-flight ガード**) |
| `541e1f3` | 全力実行で**マシンごと BSOD (0x7F_8) を2回誘発** | ページ間クールダウン + CPUスレッド上限の負荷ノブを追加 |
| `b73d1cf` | 構築中にブラウザが競合して固まる | **P-core分業プロファイル**を既定化 |
| `30b419e` | 画像単独の埋め込みが組めない | 素の `AutoModel` をやめ `SentenceTransformer.encode` (モデルの正規API) へ |

**`93dbca5` (in-flight ガード) の原因が最も非自明**: アイドル判定を「最後の実行の
**開始**時刻」基準にしていたため、1回の埋め込みが idle 閾値 (CPUで約95秒/ページ) を
超える環境では、**計算中のバックエンドを解放**してしまう。次のページで再ロードし、
また解放する、というスラッシングになった。

**`541e1f3` の BSOD** は、全24スレッドでの連続 AVX 実行が Prime95 級のストレス負荷に
なり、K付きCPU + XMP 環境の安定性マージンを超えたもの。アプリのバグではなく、
**アプリが誘発したハードウェアの不安定化**。

## 結果

- 実測 (RTX 2080 Ti機・CPU bf16・安全プロファイル = 8スレッド + 休止10秒):
  **約95秒/ページ**、50ページ完走、RSS 4.5GB 一定
- 全力プロファイル (24スレッド) は 53秒/ページだが BSOD を誘発 → **既定値は安全側**
- CUDA (cu126) は「Ollama常駐下では CPU より遅い」と判定し導入見送り
  → **この判断は ECN-005 で覆された**

## 教訓

- **「アイドル」判定は必ず in-flight 実行数を追跡する。** 基準時刻だけでは
  「暇」と「長時間実行中」が区別できない。これは推論に限らず、あらゆる
  リソースの遅延解放に当てはまる
- **ローカルで重い計算を回すツールは、負荷ノブが機能要件になる。** スレッド上限・
  バースト間休止は「あれば良い」ではなく、**入れないとユーザーのマシンが落ちる**
- **ハイブリッドCPU (P+E) ではバックグラウンドプロセスが EcoQoS で E-core に
  寄せられる。** 推論スレッドが E-core クラスタを飽和させ、ブラウザの背景処理と
  競合する。対策は EcoQoS 解除 + 少数スレッド。
  `SetProcessInformation` は **argtypes 明示が必須** — 既定の `c_int` 変換では
  64-bit HANDLE が壊れ `ERROR_INVALID_HANDLE` で常に失敗する
- **埋め込みモデルは HuggingFace の `library_name` が示す正規APIから書く。**
  素の `AutoModel` から始めて実機で直すのは二度手間だった
