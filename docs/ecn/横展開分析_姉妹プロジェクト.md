# ECN 横展開分析 — 姉妹プロジェクト

- **分析日**: 2026-08-02
- **元プロジェクト**: NotebookOllama ([[README|ECN-001〜006]])
- **対象**: 01_StatbleBlock / 04_StableState / 05_MermaidAssist / 06_PlantUMLAssist

## 結論

**横展開すべき変更は無い。** 6件中5件がアーキテクチャ差異により対象外、
1件は対象プロジェクト側で既に等価な対策が取られている。

対象4プロジェクトはいずれも**ブラウザ内で動く図エディタ** (JavaScript/HTML) で、
NotebookOllama は **Python の RAG バックエンド + GPU 推論**。ECN の大半は
後者に固有の層 (取込パイプライン・ベクタ検索・GPU 依存・SQLite) にあり、
前者には対応する構造が存在しない。

これは「調べたが何も無かった」ではなく、**「無いことを根拠付きで確認した」**
記録である。次に同じ問いが出たときに再調査しないためのもの。

## 判定の根拠

### ECN-005 (CUDA混載) — 対象外

GPU 依存を持つプロジェクトが1つも無い。

- 01 / 05 / 06: Python の依存自体が無いか、あっても GPU 非依存
  (`06_PlantUMLAssist/server.py` は標準ライブラリのみの静的配信 + PlantUML 呼び出し)
- 04: `mcp-server/pyproject.toml` の依存は `mcp[cli]` と `pydantic` のみ。
  torch / CUDA ライブラリを一切引かない

CUDA メジャー版の混載という問題パターンが**発生する条件が無い**。

### ECN-006 (SQLiteスキーマ移行) — 06 は該当なし、他は対象外

SQLite を使っているプロジェクトは無い (検索ヒットは venv 内の pygments のみ)。

ただし **06_PlantUMLAssist は localStorage に構造化データを永続化**しており、
「保存済みユーザーデータの形が変わったときどうするか」という**同型の問題**を持つ。

**既に対策されている**: `src/core/auto-save.js:115` の設定読み出しが
**フィールド単位の検証 + 既定値フォールバック**になっている。

```javascript
out.backend = (stored.backend === 'localStorage' || stored.backend === 'file')
              ? stored.backend : DEFAULTS.backend;
```

未知の値・欠損フィールドが来ても壊れない。ECN-006 が SQLite で
「テーブル再作成 + 冪等判定」で達成したことを、JS 側は
**寛容な読み出し (tolerant reader)** で達成している。方式は違うが目的は同じで、
移植する必要は無い。

> [!note] 監視ポイント
> `auto-save.js:33-35` の `KEY_META` は `JSON.parse` した結果をそのまま使っており、
> 設定と違ってフィールド単位の検証が無い。meta の**構造**を変える改修が入るときは、
> ECN-006 の「冪等判定はスキーマの実体を見る」という考え方が参考になる。
> 現時点では meta の形は変わっていないため**該当なしのまま**。

### ECN-003 (負荷ノブ) — 対象外

「重い計算がユーザーのマシンを不安定にする」という問題パターン。
対象4プロジェクトはブラウザ内の図レンダリングで、CPU を数分間飽和させる
処理を持たない。

**ついでに確認した点** (結果は問題なし):

- 05_MermaidAssist は再描画を `requestAnimationFrame` で束ねている
  (`src/app.js:785-786`)。固定 ms の debounce より適切で、変更不要
- 06_PlantUMLAssist の `debounceMs: 1000` は**自動保存**の間隔であり
  プレビュー描画ではない。UI から変更可能。描画応答性の問題ではない
- 01 / 04 には該当する debounce 処理が見当たらなかった

### ECN-001 / 002 / 004 — 対象外

- **001**: 取込パイプライン・サーバー側永続化・段階リリースの枠組みが
  どのプロジェクトにも無い。ベータフラグ基盤も、現状これらは
  バージョン単位でリリースしており必要としていない
- **002**: LLM を組み込んでいるプロジェクトが無い
  (検索ヒットは venv 内・ブレインストーム成果物・テストファイルのみ)
- **004**: ベクタ検索そのものが無い

## 将来 LLM 機能を足すときに読むべきもの

現時点では対象外だが、**図エディタに LLM 支援 (自然言語→DSL 生成など) を
足す構想が出た時点で**、以下は前提知識として有効:

1. **[[ECN-002_VLM図説明とスキャンPDF-OCR|ECN-002]] の教訓** —
   LLM の失敗は例外ではなく**もっともらしい出力**で返る。
   「この図は生成できません」がそのまま DSL として保存される事故が起きうる。
   保存直前の妥当性検査が要る
2. **[[ECN-002_VLM図説明とスキャンPDF-OCR|ECN-002]] の Lazy 化** —
   モデル選択の設定値は起動時ではなく**実行時**に解決する。
   起動時に掴むと「設定を変えても効かない」というバグになる
3. **[[ECN-003_視覚埋め込み第2インデックスとRRF融合|ECN-003]] の負荷ノブ** —
   ローカル推論を回すなら、スレッド上限とバースト間休止は
   「あれば良い」ではなく**入れないとユーザーのマシンが落ちる**

## 補足: ポート 8766 の衝突に注意

`06_PlantUMLAssist/server.py` は **PORT = 8766** を使う。
NotebookOllama の隔離実機検証でも 8766 を使う運用になっているため、
両方を同時に起動すると衝突する。実機検証の前に `netstat` で確認すること
(本番 8765 を避けるだけでは足りない)。
