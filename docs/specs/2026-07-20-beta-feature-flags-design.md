# 汎用ベータ機能フレームワーク (Feature Flags) 設計書

## 1. 背景と目的

影響範囲の大きい機能(第1号: 表・図シリーズ Stage 1〜3)を、いきなり全ユーザーの既定動作にせず**ベータとしてオプトインしたユーザーにのみ提供**したい。またベータ機構は今後の機能でも繰り返し使うため**汎用基盤**とし、評価が済んだら**簡単に正式版(GA)へ昇格**できる動線を最初から設計に含める。

本アプリはローカル個人アプリでユーザーアカウント概念がないため、「承認したユーザーのみに提供」は**アプリ設定でのオプトイン**をもって承認とみなす。

## 2. 要求(ユーザー要件)

1. 設定でベータ機能を有効化するか選べる(既定OFF、オプトイン)
2. ベータ機構は汎用的で、今後の機能にもそのまま使える
3. ベータ→正式版の移行動線が明確で、承認時の昇格が簡単(最小の変更で完了)

## 3. スコープ

### 対象 (in)

- フラグレジストリ(コード内宣言、single source of truth)
- 設定でのオプトイン永続化と設定画面「ベータ機能」セクション
- バックエンド/フロントエンド/MCPのゲーティング機構
- GA昇格動線(レジストリ1行変更+昇格チェックリスト)
- 第1号適用: `table-figure-rag`(表・図シリーズ全体で1フラグ)

### 対象外 (out)

- フラグ間依存の宣言機構(現時点で単一フラグのため不要。必要になった時に本specを改訂)
- 段階的ロールアウト率・A/B配信(個人アプリに不要)
- 既存機能(開発者モード等)のフラグ基盤への移設(将来候補として付記のみ)

## 4. アーキテクチャ

```
core/features.py(レジストリ: 宣言のみ)
  FeatureFlag(id, name, description, stage: 'beta'|'ga', since, spec)
        │
        ├─ settings_store: beta_optins = {flag_id: bool}(既定false)
        │
        ├─ 判定: features.is_enabled(flag_id) =
        │     stage=='ga' → 常にTrue(オプトイン値は無視)
        │     stage=='beta' → beta_optins[flag_id] == True
        │
        ├─ BE: FastAPI依存 require_feature(flag_id) → 無効時403+
        │     「設定のベータ機能で有効化してください」ヒント(既存503+ヒントと同型)
        ├─ FE: GET /api/features → {id,name,description,stage,enabled}[]
        │     設定画面はstage=='beta'のみトグル表示。UI各所はenabledマップで出し分け
        └─ MCP: ベータ機能が追加するツール/挙動は無効時に非公開
```

- レジストリはコード内宣言に限定する(DBにフラグ定義を持たない)。フラグの追加・昇格・廃止がすべてコードレビュー(git履歴)に乗り、「どの版でGAになったか」が追跡できる
- パイプライン内部の分岐(取込時の抽出段など)も同じ `is_enabled` を参照する

## 5. API / UI(evaluatorスクショ検証ゲート対象)

- API: `GET /api/features`(全フラグと状態)、`PUT /api/features/{flag_id}`(`{"enabled": bool}`、GAフラグへのPUTは400)
- UI: 設定画面に「ベータ機能」セクションを新設。フラグ毎にトグル+説明+specへのリンク。ベータフラグが0件のときはセクション自体を非表示(縦肥大化なし)
- トグルON時に確認ダイアログ等は出さない(オプトイン操作自体が承認)。OFF→ONは即時反映、ON→OFFも即時(データは保持、§7)

## 6. GA昇格動線

**昇格 = レジストリの `stage: 'beta'` を `'ga'` に変える1行変更**で完了する。これを成立させるための設計規約:

- ゲートは必ず `is_enabled` / `require_feature` を経由する(フラグ状態の直接参照を書かない)。GA化で全ゲートが自動的に常時有効になり、コード掃除なしで正式版動作になる
- ベータ期間に作られたデータ(例: chunk_assets)はスキーマ上ベータ非依存で作る(昇格でマイグレーション不要)
- 昇格チェックリスト(specテンプレとして規約化):
  1. レジストリ `stage` を `'ga'` に変更(トグルは設定画面から自動で消える)
  2. 対象specの `status` を `approved` に更新+MOCアイコン更新
  3. ADRドラフトの採番申請(承認後 `/adr`)
  4. (任意・後日)ゲート呼び出しの撤去リファクタ — GA直後は必須としない
- **ベータ中止**の動線も定義する: レジストリからフラグを削除し、ゲート箇所をコンパイルエラー/テストで洗い出して撤去。データは削除しない(§7)

## 7. データ規約(無効時・中止時)

- ベータONの期間に生成されたデータ(サイドカー、チャンク、インデックス)は、OFFに戻しても**削除しない**。機能の露出(UI/API/検索への反映)だけが消える
- 例外として、チャンク本文に混入済みの派生テキスト(Stage 1のMarkdown表など)はOFF後も本文に残る。完全に元へ戻すには当該ソースの再取込が必要である旨を、各機能specのOFF時挙動節に明記する
- 各ベータ機能のspecは「**フラグOFF時の挙動**」を1節で必ず定義する(本フレームワークの規約)

## 8. エラー処理

- 無効フラグのAPI呼び出し: 403+有効化ヒント(存在は秘匿しない。ローカル個人アプリのため発見可能性を優先)
- レジストリに存在しないflag_idへのPUT: 404
- settings_storeに残った廃止フラグのオプトイン値: 読み捨て(レジストリ照合時に無視、次回保存で掃除)

## 9. テスト

- **unit**: is_enabledの判定表(beta×オプトイン有無、ga、未知id)、GAフラグへのPUT拒否、廃止フラグ値の読み捨て
- **integration**: /api/features の一覧・更新、require_feature依存の403とヒント、フラグOFF時にゲート対象APIが遮断されること
- **UI**: evaluator実機スクショで設定画面のベータ機能セクション(トグル表示・0件時非表示)、OFF時にUI露出が消えること

## 10. QAログ(推奨値で先行決定した非クリティカル論点)

| 論点 | 決定(推奨値) | 理由 |
|---|---|---|
| フラグ定義の置き場所 | コード内レジストリ(DB定義なし) | 昇格・廃止をgit履歴で追跡、レビューに乗せる |
| 無効時のAPI応答 | 403+有効化ヒント | 既存の503+ヒントパターンと同型、発見可能性優先 |
| オプトインの粒度 | アプリ全体(ノートブック単位にしない) | 設定の単純さ、個人アプリの実態に合致 |
| 開発者モードの移設 | しない(将来候補として付記のみ) | スコープ最小化 |
| フラグ間依存機構 | v1では持たない | 第1号が単一フラグのためYAGNI |

## 11. 第1号適用: table-figure-rag

- 表・図シリーズ(Stage 1〜3)は**シリーズ全体で1フラグ** `table-figure-rag`(表示名: 表・図検索強化)としてベータ提供する(ユーザー決定)
- 実装済みのステージから順次このフラグ配下で機能が増える(分割実施)。GA昇格はシリーズとして1回
- 各StageのspecにOFF時挙動の節を追記する(本spec承認と同時に反映済み)

## 12. 起票予定のADRドラフト(spec承認後に作成)

1. **機能提供はコード内フラグレジストリ+設定オプトインのベータ機構** — GA昇格=stage 1行変更、データはベータ非依存スキーマ(カテゴリ: アーキテクチャ/リリース管理)
